## D-01 · Bot API + launchd вместо `tgsend`

**Дата:** 2026-11-16 · **Статус:** принято

**Решение.** Бот работает через Telegram Bot API (long polling, `getUpdates`) как отдельный
python-процесс под launchd. `tgsend` (UI-скрипт в «Избранное») в коде не используется.

**Причина.** `tgsend` — односторонний UI-скрипт: открывает Telegram, жмёт Cmd+K, вставляет
через меню, зависит от фокуса и раскладки; принять ответ пользователя и вести диалог он не
может. Bot API даёт приём сообщений, команды, `retry_after` при 429 и `409` при двойном
запуске. DSH-сессии в фоне не живут — фоновость даёт launchd + `/usr/local/bin/python3`.

**Следствия.**
- `src/telegram.py` (235 строк): `call/send/get_updates`, разбивка >4000 символов, `TelegramError`.
- `src/main.py` (466): цикл `get_updates(offset, 20)` + `tick()`, pid-лок `data/lifeos.pid`.
- `ops/com.lifeos.agent.plist`: `RunAtLoad` + `KeepAlive` + `WorkingDirectory=__APP_DIR__`.
- `install.sh` (739 строк): копирование в `~/Library/Application Support/LifeOS`,
  `launchctl bootstrap gui/$UID` с fallback на `load -w`.
- `tgsend` остаётся личным инструментом пользователя (см. `~/.dsh/AGENTS.md`), не частью продукта.

**Где видно:** `PROJECT_CONTEXT.md` §4, `ТЗ.md` §3.1/§3.7, `src/main.py`, `ops/*.plist`.

## D-02 · LLM опционален, скриптованный fallback

**Дата:** 2026-11-16 · **Статус:** принято

**Решение.** Любой вызов LLM может вернуть `None`; бот продолжает диалог на заранее
заготовленных вопросах и эвристике разбора. Данные сохраняются всегда.

**Причина.** SAMP-гейтвей нестабилен (ранее `glm-5.3-prime` отдавал `tools_unsupported`),
ключа у пользователя может не быть; по ТЗ §3.4 и §9 бот не должен зависеть от LLM.

**Следствия.**
- `LLM.chat/json_chat` не бросают исключений: сеть/таймаут/5xx/битый JSON → `None`
  (`src/llm.py`, docstring модуля); ключ и тела в логи не пишутся.
- `parsing.parse_answer` при недоступном LLM: категория по ключевым словам/слоту, `title`
  из первой строки, `metrics {}` (`src/parsing.py`).
- `scheduler._FALLBACK_QUESTIONS` (`src/scheduler.py:69`) и `_FALLBACK_GREETINGS` (:93) —
  полный сценарий без LLM; `_CLOSING_TEXTS` (:99).
- `install.sh` подставляет `DDD_API_KEY` из `~/.dsh/.credentials.yaml`, если он есть; без
  ключа установка не падает.

**Где видно:** `tests/test_parsing.py` (7 fallback-тестов),
`tests/test_scheduler.py::test_free_text_without_llm`.

## D-03 · SAMP: явный User-Agent (403 Cloudflare 1010)

**Дата:** 2026-11-16 · **Статус:** принято

**Решение.** Все запросы к SAMP идут с `User-Agent: LifeOS/1.0`; модель по умолчанию —
`deepseek-v4.1-flash-1017`, база — `https://api.samp.team/v1`.

**Причина.** Cloudflare у шлюза SAMP отвечает `403 error 1010` на дефолтный
`Python-urllib/3.x`. Проверено 2026-11-16 (комментарий в коде). `glm-5.3-prime` признан
больным и не используется.

**Следствия.**
- `USER_AGENT` (`src/llm.py:32`), заголовок в запросе (`src/llm.py:250`).
- `DEFAULT_BASE_URL`/`DEFAULT_MODEL` (`src/llm.py:27-28`).
- При 429 — один повтор с паузой ≤5 с (`MAX_RETRY_SLEEP`), всего 2 попытки.
- Диагностика в логе — только код ошибки, без тела ответа.

**Где видно:** `src/llm.py:31-32`, `:250`; `tests/test_parsing.py` (LLM-моки).

## D-04 · Self-contained дашборд без CDN

**Дата:** 2026-11-16 · **Статус:** принято

**Решение.** `dashboard/index.html` — один файл: стили, JS и данные внутри; открывается
двойным кликом без интернета. Рядом кладётся `data.json` для машинного чтения.

**Причина.** ТЗ §3.6/§7: офлайн, никаких CDN и внешних шрифтов; приватность (данные не
уходят в сеть); пользователь не запускает сервер.

**Следствия.**
- `dashboard/template.html` 701 строка, дизайн-токены в `:root` (`--bg:#F6F7FB`,
  `--violet:#A18BB7`, радиус 20 px, тень `0 8px 24px rgba(23,24,28,.06)`).
- Данные встраиваются как `window.LIFEOS_DATA` (`dashboard/template.html:275`).
- `build_dashboard` пишет `index.html` + `data.json`, возвращает путь; ошибки → `None`.
- Внешних URL нет: grep по `http(s)://` даёт только XML-namespace `http://www.w3.org/2000/svg`
  (не сетевой запрос) и ссылки `obsidian://` на цели.

**Где видно:** `src/dashboard_data.py` (927), `dashboard/template.html`, `demo/index.html`.

## D-05 · Только стандартная библиотека Python

**Дата:** 2026-11-16 · **Статус:** принято

**Решение.** Никаких `pip`-пакетов, npm и внешних бинарников. Всё на stdlib.

**Причина.** Проект должен ставиться на чистый Mac и работать под launchd без venv;
ТЗ §4/§7 и PLAN.md запрещают зависимости; меньше точек отказа при обновлении macOS.

**Следствия.**
- HTTP: `urllib.request`; БД: `sqlite3` (WAL, `busy_timeout`); время: `zoneinfo`;
  мок-сервер: `http.server`; логи: `logging.handlers.RotatingFileHandler`.
- Нет `requirements.txt`; тесты — `unittest`.
- Цена: свой HTTP-клиент (235 строк), своя ротация логов, нет `requests`/`dateutil`.

**Где видно:** `src/*.py` (импорты), `install.sh` (проверка интерпретатора), `INTERFACES.md` §14.

## D-06 · Совместимость с Python 3.9

**Дата:** 2026-11-16 · **Статус:** принято

**Решение.** Код и установщик обязаны работать на Python 3.9+; установщик выбирает
подходящий интерпретатор и проверяет версию.

**Причина.** На Mac два Python: `/usr/bin/python3` = **3.9.6** (системный, его может взять
launchd) и `/usr/local/bin/python3` = **3.13.14**. Если писать под 3.13, на 3.9 бот упадёт
на старте — а это самый вероятный сценарий у пользователя.

**Следствия.**
- `from __future__ import annotations` во всех модулях; без `match`, без рантайм-`X | Y`.
- `install.sh:162` проверяет `sys.version_info >= (3, 9)`; приоритет `/usr/local/bin/python3`,
  затем `/usr/bin/python3`; `LIFEOS_PYTHON` — override для отладки.
- В plist подставляется выбранный интерпретатор (шаблон содержит `/usr/bin/python3`,
  `install.sh` заменяет на фактический).
- Цена: синтаксис 3.10+ недоступен.

**Где видно:** `install.sh:162,170-173`; прогон тестов на 3.13 — `TEST_HISTORY.md` §1.

## D-07 · Шаблон дашборда переписан Lead'ом после потери контекста

**Дата:** 2026-11-16 (16:34) · **Статус:** принято

**Решение.** `dashboard/template.html` собран Lead'ом заново; dash-агент отвечал только за
`src/dashboard_data.py` и данные. Дизайн-токены — из `PROJECT_CONTEXT.md` §3.

**Причина.** `dashboard_data.py` был сдан в 16:23, а шаблон к этому моменту отсутствовал:
dash-агент потерял контекст и не отдал `template.html`. Без шаблона `build_dashboard`
возвращает `None` (это зафиксировано тестом `test_build_without_template_returns_none`),
то есть продукт без дашборда.

**Следствия.**
- `dashboard/template.html` — 701 строка, 37 523 Б, 16:34; демо `demo/index.html` 41 785 Б
  и `demo/data.json` 7 084 Б собраны тогда же.
- Контракт `collect_data` не менялся — шаблон потребляет готовую схему (§9 INTERFACES).
- Шаблон фактически стал зоной Lead'а; `tests/test_dashboard.py` проверяет сборку как с
  проектным шаблоном, так и с кастомным/отсутствующим.
- Риск на будущее: правки дизайна теперь идут через Lead'а, а не через dash-агента.

**Урок:** шаблон — отдельный артефакт с ранним сроком сдачи, а не «соберём в конце».

**Где видно:** mtime `dashboard/template.html` (16:34) vs `src/dashboard_data.py` (16:23);
`tests/test_dashboard.py`.

## D-08 · `write_mirror` вызывается из scheduler/main, а не только из Vault

**Дата:** 2026-11-16 · **Статус:** принято

**Решение.** Зеркало данных (`Life OS/data/entries.jsonl`, `goals.json`) обновляет
планировщик через `Scheduler._write_mirror_safe()` — после каждой записи ответа, после
`/add_goal`, в ролловере дня и при старте/синке.

**Причина.** По контракту (INTERFACES §7) метод `write_mirror` живёт в `Vault`, но вызывать
его должен тот, кто меняет данные. Иначе зеркало отстаёт до следующего `sync_pending`
(раз в тик/старт), и Dataview-запросы пользователя видят устаревшие данные.

**Следствия.**
- `_write_mirror_safe()` — `src/scheduler.py:968-990`: собирает все entries, зовёт
  `vault.write_mirror`, ловит любые ошибки, пишет warning.
- Вызовы: `:542` (после записи ответа), `:745` (после добавления цели), `:890` (ролловер),
  `:952` (старт/синк).
- Падение зеркала не роняет диалог: данные уже в SQLite и дневнике.
- При `obsidian.write_mirror=false` вызовы становятся no-op (проверено тестом
  `test_write_mirror_disabled_by_config`).

**Где видно:** `src/scheduler.py:968-990` и точки вызова; `src/obsidian.py` (`write_mirror`).

## D-09 · Недельный слот отложен (выключен по умолчанию)

**Дата:** 2026-11-16 · **Статус:** принято

**Решение.** `weekly` есть в коде и конфиге, но `"enabled": false`. Дайджест-заметка
`01 Daily/Неделя YYYY-Www.md` в v0.1 не создаётся.

**Причина.** ТЗ §2 и §10 относят недельный дайджест к фазе 2 («nice-to-have»), приёмка
(ТЗ §8) от него не зависит. Приоритет — три ежедневных слота и стабильность.

**Следствия.**
- `config/config.example.json:37-41`: `"weekly": {"time":"21:00","weekday":6,"enabled":false}`.
- Код слота покрыт тестом `test_weekly_slot_starts_on_configured_weekday` — включение не
  потребует переписывания планировщика.
- Включение: `"enabled": true` (+ `weekday`), затем `bash install.sh --reload`.
- `prompts.weekly_prompt(stats)` существует, но ночная сборка заметки недели — в backlog #1.

**Где видно:** `config/config.example.json:37-41`, `src/scheduler.py` (`_SLOT_ORDER`, weekly),
`tests/test_scheduler.py`.

## D-10 · Сематика целей: прогресс = current/target; дефект «вес 78 кг = 100%»

**Дата:** 2026-11-16 · **Статус:** принято (дефект зафиксирован, фикс — v0.2)

**Решение.** В v0.1 прогресс цели считается как `current / target` с обрезкой в 0..1;
направление цели (рост/снижение) не учитывается. Дефект не блокирует релиз, вынесен в
`QUALITY_BACKLOG.md` #3.

**Причина/механика.** `_goal_progress` (`src/dashboard_data.py:430-458`) берёт числа из
`current`/`target`, при отсутствии — процент из текста, иначе 0. Для цели «Похудеть до 78 кг»
пользователь задаёт `target = "78"`, а текущий вес тоже 78 → `78/78 = 1.0` → **100%**,
хотя это только начало пути. Любая цель, где `current >= target`, тоже показывает 100%.

**Воспроизведение (2026-11-16, 16:38):**
```
goal 1: "Похудеть до 78 кг", target "78 кг", current "78"  → progress 1.0
goal 2: "Пробежать 10 км",   target "10",    current "3"   → progress 0.3
```
Тот же дефект уже в демо: `demo/data.json` → цель «Вес 78 кг», `progress: 1.0`.

**Следствия.**
- Данные не теряются, БД и Obsidian корректны — врёт только визуализация.
- В `RELEASE_NOTES.md` — known issue; в backlog #3 — формула с направлением и стартовым
  значением: `(start - current) / (start - target)` для убывающих целей.
- Пользователю в v0.1: для убывающей цели писать прогресс вручную (`/add_goal … | 3/10`),
  а не полагаться на авторасчёт из веса.

**Где видно:** `src/dashboard_data.py:430-458`; `demo/data.json`; прогон в `TEST_HISTORY.md` §2.5.

## D-11 · Один процесс: pid-лок и аккуратное завершение

**Дата:** 2026-11-16 · **Статус:** принято

**Решение.** Второй экземпляр агента не запускается: `data/lifeos.pid` + проверка живости
через `os.kill(pid, 0)`; сигналы SIGTERM/SIGINT закрывают БД и снимают лок.

**Причина.** Telegram отдаёт `409 Conflict` при двух `getUpdates`; пользователь может
запустить `python3 src/main.py` вручную при работающем launchd (ТЗ §9).

**Следствия.** `src/main.py:46` (`PID_RELATIVE_PATH`), `:50` (`_pid_alive`), `:66-97`
(класс лока), `:82` — битый pid-файл не блокирует запуск. KeepAlive перезапускает только
упавший процесс, не создавая второй.

**Где видно:** `src/main.py`; `README.md` §9 (раздел про 409).

## D-12 · Демо-дашборд на синтетических данных

**Дата:** 2026-11-16 (16:34) · **Статус:** принято

**Решение.** Для показа пользователю собран `demo/index.html` + `demo/data.json` на
синтетике (14 дней, 3 цели, 2 привычки, 5 записей), отдельно от боевой БД.

**Причина.** Реальных записей ещё нет, а пустой экран не показывает дизайн; ТЗ §3.6 требует
аккуратные пустые состояния, но оценить «похоже на референс» по ним нельзя.

**Следствия.** Демо статично и не обновляется; прод-дашборд собирается из SQLite в
`dashboard/index.html` (+ `data.json`). Демо-данные специально включают проблемную цель
«Вес 78 кг» (см. D-10).

**Где видно:** `demo/` (16:34), `src/dashboard_data.py::build_dashboard`.
