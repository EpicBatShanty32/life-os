# WORKFLOW — жизненный цикл задачи в студии Life OS

**Дата:** 2026-11-17 · **Основа:** `ТЗ.md`, `studio/PROJECT_BIBLE.md`, `TASK_LEDGER.md`,
`DECISION_LOG.md`, `QUALITY_BACKLOG.md`, `AGENT_PERFORMANCE.md`, `TEST_HISTORY.md`,
скиллы `writing-plans`, `executing-plans`, `verification-before-completion`,
`requesting-code-review`, `commit`.
**Главное правило:** «готово» = файл + прогон + строка в памяти. Слова в чате доказательством
не считаются (`TEST_HISTORY.md` §5, `AGENT_PERFORMANCE.md` урок 5).

## 1. Приём задачи

- Владелец называет боль и пункт ТЗ: `ТЗ.md` §..., `PROJECT_BIBLE.md` §2. Без боли задачу
  не берём (`QUALITY_BACKLOG.md`, «Как пополнять» п.2).
- Lead формулирует «done»: 3–5 критериев, каждый проверяется командой или файлом. Образец:
  «прогресс убывающей цели → тест в `tests/test_dashboard.py`» (`QB-03`).
- Задача получает `T-N` в `TASK_LEDGER.md`: владелец, статус, поля «Результат» и «Отчёт».
- Готово, когда: критерии закрыты, прогон показывает число тестов и rc, артефакт лежит в
  проекте, строка `T-N` закрыта владельцем или Lead'ом.
- Внешний блокер (токен, доступ, чужой файл) — статус `блок`, а не «в работе» (T8).

## 2. План

- План письменный: на волну — `PLAN.md`, на задачу — `studio/plan-T<N>.md`; строка `T-N` в
  `TASK_LEDGER.md` ссылается на файл.
- Внутри: цель, границы («не входит» → ТЗ §10 или `QUALITY_BACKLOG.md`), таблица
  «файл → владелец → тест», порядок работ, команда прогона.
- Один файл — один владелец. Двое на один файл — ошибка нарезки: переписываем план, а не
  договариваемся в чате.
- Файл длиннее 600 строк дробится до старта, комфортный размер — 400–600: `scheduler.py`
  1320, `obsidian.py` 1048, `dashboard_data.py` 927 — так агенты теряли контекст
  (`AGENT_PERFORMANCE.md` урок 1).
- Контракт (импорты, сигнатуры, формат данных) — в `INTERFACES.md`, не в переписке.
- Артефакт «сделаю в конце» получает файл-заглушку и срок сразу: `template.html` потеряли,
  Lead писал заново (`DECISION_LOG.md` D-07).
- План проходит чек-лист PLAN (`CHECKLISTS.md`).

## 3. Исполнение

- Агенты идут волной; у каждого свои файлы и свой тест-файл. Общие фикстуры —
  `tests/_support.py`, владелец qa.
- Сначала тест: падает по нужной причине (RED), потом код (GREEN). Упавший прогон читаем,
  а не перезапускаем.
- Прогон до и после правки: `python3 -m unittest discover -s tests -p test_<модуль>.py -v`.
- Всё, что пишет на диск, — в `tests/tmp` или `mktemp`. Живая база Obsidian в тестах
  не трогается (`AGENT_PERFORMANCE.md` урок 8).
- Секреты — только в `config.json` (права 600) и env; в логах, тестах и коммитах их нет.
- Lead не берёт продуктовый код, пока есть свободный исполнитель: его зона — контракты,
  стыки, приёмка. Цена нарушения — D-07 (сам переписывал шаблон).
- Правка одного файла не размазывается по волне: поздние строки ломают ранние.

## 4. Ревью

- Ревьюер получает диапазон `BASE..HEAD` (`git log --oneline`, `git diff`), пункт ТЗ и вывод
  прогонов. Ревью без файла не существует (`AGENT_PERFORMANCE.md`, строка review).
- Проверяет: диф соответствует ТЗ и не делает лишнего; тесты прогнаны им самим; края —
  размер, кодировка, гонка, чужой текст (`ADVERSARIAL_REPORT.md`: 7 из 12 pid-локов,
  250k → 63 сообщения); README совпадает с поведением; секретов нет; живая база цела.
- Зелёный suite — не доказательство: четыре проверки нашли 13 блокеров при 150 тестах
  (`AGENT_PERFORMANCE.md` урок 9).
- Вердикт — файл `REVIEW.md` или отчёт роли. Строка:
  `P0|P1|P2 | file:line | симптом | как воспроизвести | что исправить`.
  Итог: «готово к релизу» или «не готово: N пунктов».
- P0 — стоп волны; P1 — фикс до релиза; P2 — в `QUALITY_BACKLOG.md`. Несогласие с
  ревьюером — тестом или цитатой из ТЗ, не «мне кажется».

## 5. Релиз

- Сначала реестр блокеров: открытых P0/P1 нет (`RELEASE_NOTES.md`, `QUALITY_BACKLOG.md`).
- Unit на 3.13: `python3 -m unittest discover tests -v` → OK, число тестов записать.
- Unit на 3.9: `/usr/bin/python3 -m unittest discover tests -v` → OK. В `TEST_HISTORY.md`
  такого прогона нет, только `compileall`; пробел закрыть на этом релизе.
- `compileall` на 3.9.6 и 3.13:
  `env PYTHONPYCACHEPREFIX=$(mktemp -d) /usr/bin/python3 -m compileall -q src` → rc=0, то же `python3`.
- E2E: `python3 tests/e2e_mock.py` → rc=0, все проверки.
- Самопроверка: `bash check.sh` → `PASS`, 11 проверок.
- Бэкап базы Obsidian до записи в неё: копия каталога из `PROJECT_CONTEXT.md` §1.
- Версия по порядку: `CHANGELOG.md` → `VERSION` → `src/__init__.py:__version__` →
  `RELEASE_NOTES.md` (корень) → `studio/RELEASE_NOTES.md` → тег («Правила выпуска»).
- Коммит по скиллу `commit`: `git status --short`, `git diff`, стейдж по смыслу, сообщение
  `<область>: <что>`, без секретов и мусора. Пуш — только по просьбе владельца.
- Заметка о выпуске и строка прогона — в `RELEASE_NOTES.md` и `TEST_HISTORY.md`; затем
  чек-лист RELEASE (`CHECKLISTS.md`).

## 6. Память

| Куда | Что пишем | Когда |
|---|---|---|
| `DECISION_LOG.md` | решение, причина, следствия, «где видно»; отменённое — `ОТМЕНЕНО` | необратимое решение |
| `TASK_LEDGER.md` | `T-N`, владелец, статус, результат путями и цифрами, файл-отчёт | взял / закрыл |
| `TEST_HISTORY.md` | дата, команда, число тестов, rc, ссылка на вывод | каждый прогон |
| `AGENT_PERFORMANCE.md` | вклад в файлах и тестах, где споткнулся, урок | после волны |
| `QUALITY_BACKLOG.md` | долг: боль, фикс, объём S/M/L, приоритет, критерий | идея / дефект |

- Побочно: `PROJECT_BIBLE.md` — границы и DoD, `ARCHITECTURE_MAP.md` — структура,
  `RELEASE_NOTES.md` — версии, `SKILLS.md` — что умеет какая роль.
- В записи — путь и число. Пересказ чата памятью не считается (`AGENT_PERFORMANCE.md` урок 5).
