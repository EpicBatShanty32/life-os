## P1 (важное — чинить до живой установки)

### P1-1. Offset `getUpdates` не сохраняется → повторная обработка апдейтов после рестарта/сбоя

**Файлы:** `src/main.py:399` (`offset: int | None = None` при каждом старте),
`src/main.py:410` (`get_updates(offset, ...)`), `src/main.py:440` (offset живёт
только в памяти). `src/scheduler.py` не дедуплицирует по `update_id`.

**Симптом.** Telegram подтверждает пачку апдейтов только следующим вызовом
`getUpdates` с `offset`. Если процесс завершился (SIGTERM/SIGKILL/краш/перезагрузка)
между обработкой пачки и следующим опросом, на старте `offset=None` → Telegram
**отдаёт эту пачку повторно** → бот повторно отвечает, повторно пишет запись и,
если это был ответ в сессии, **сдвигает сессию второй раз** (вопрос пропускается).

**Воспроизведение.**
1) Локально (сделано): создать `Scheduler`, `tick` в 21:30 (старт сессии), вызвать
   `on_message(...)` один раз; создать заново `Scheduler` на той же БД (имитация
   рестарта) и вызвать `on_message` с тем же текстом → в `entries` 2 записи,
   сессия ушла на следующий вопрос.
2) На моке: `tests/e2e_mock.py` изначально падал именно на проверке
   «повторный запуск не дублирует слот» (`/help`, отправленный прямо перед SIGTERM,
   приходил повторно). Сейчас тест **обходит** проблему, дожидаясь подтверждения
   очереди перед остановкой (`tests/e2e_mock.py:425-430,493-494`), т.е. баг в коде
   остался, а тест его больше не ловит.

**Фикс (маленький).** Хранить offset в kv: после `_handle_updates` писать
`storage.kv_set("tg_offset", str(offset))`, на старте читать
`offset = int(kv_get("tg_offset") or 0) or None`. Дополнительно (защита от
повторной доставки при рассинхроне) — хранить `last_update_id` и пропускать
`update_id <= last_update_id`. Добавить в e2e проверку повторной доставки
(несколько раз вызвать `getUpdates` без offset на моке).

### P1-2. `--dry-run` не изолирован: пишет в рабочую БД/kv, в Obsidian и «съедает» слот дня

**Файлы:** `src/main.py:315-333` (Vault создаётся всегда, `obsidian.enabled` не
меняется), `src/main.py:349-351` (в dry-run подменяется **только** Telegram),
`src/main.py:443-446` (tick выполняется как обычно). README рекомендует именно
эту проверку: `README.md:302-306` (`python3 src/main.py --dry-run --once`).

**Симптом (воспроизведено на temp-конфиге с заполненным chat_id):**
после `--once --dry-run` в рабочей БД:
`kv: session=<активная сессия>, last_slot:midday=2026-11-16, last_rollover=...`,
`messages: 1`; в Obsidian созданы `Проекты/Life OS/Цели.md` и
`Life OS/data/{entries.jsonl,goals.json}`. Последствия:
* реальный агент в этот день **не задаст вопрос слота** (`last_slot` уже стоит),
  а пользователь сообщения не получал;
* в kv висит «сессия», и следующее сообщение пользователя трактуется как ответ
  на невиданный вопрос, через 3 ч придёт «продолжим с того же места»;
* при запуске из репозитория без `config/config.json` конфиг берётся из
  `config/config.example.json`, где `vault_path` — **живая база пользователя**:
  dry-run создаст там файлы целей/зеркала (проверка «папка не найдена» есть
  только в main, но папка существует, поэтому молча пишет).

**Фикс.** В `--dry-run`: отдельная БД (`paths.db` + `.dryrun`, либо `:memory:`),
`vault = None` (или принудительно `obsidian.enabled=False`), не сохранять
`last_slot`/`session` (или восстанавливать kv после прогона). Минимум — громкое
предупреждение в README и в лог, что dry-run меняет состояние.

### P1-3. Токен бота может попасть в лог при неверном `telegram.api_base`

**Файлы:** `src/telegram.py:133-142` — `urllib.request.Request(...)` строится
**до** `try` (сам `try` начинается на `src/telegram.py:143`); исключения
`ValueError`/`InvalidURL` летят мимо `TelegramError` и содержат полный URL
с токеном. Дальше они логируются как «неожиданные»:
`src/main.py:435-437` (`logger.exception("Неожиданная ошибка при опросе Telegram: %s", exc)`)
и `src/scheduler.py:245-272` (`_send`, warning с текстом исключения).

**Воспроизведение (сделано):**
```python
Telegram("123:ABC-SECRET-TOKEN", api_base="api.telegram.org").call("getMe")
# ValueError: unknown url type: 'api.telegram.org/bot123:ABC-SECRET-TOKEN/getMe'
```
То же с управляющими символами/переводом строки в `api_base`. В main такое
исключение уходит в `agent.log` вместе с токеном — нарушение ТЗ §7 / INTERFACES §14.

**Фикс.** Строить `Request` внутри `try`, ловить `(ValueError, urllib.error.InvalidURL)`
и поднимать `TelegramError("Некорректный telegram.api_base: проверьте https://...")`
без URL; либо валидировать `api_base` в `config.py` (схема `http(s)://`, без
пробелов/управляющих символов). В текстах ошибок не интерполировать `_url`.

### P1-4. Логи: ТЗ/install/README обещают `~/Library/Logs/LifeOS/agent.log`, фактически агент пишет в другое место; часть модулей — вообще мимо файла

**Файлы:** `src/main.py:109-116` (`_setup_logging` берёт `cfg["paths"]["logs"]`),
`config/config.example.json:45` (`"logs": "data/logs"`) → реальный лог
`…/Application Support/LifeOS/data/logs/agent.log`. При этом:
`install.sh:37,46,126` и `ops/com.lifeos.agent.plist:25-28` ведут
`~/Library/Logs/LifeOS/agent.log` (туда идёт только stdout/stderr launchd),
`README.md:133,243,318` велит смотреть именно `~/Library/Logs/LifeOS/agent.log`.
`install.sh` **не прописывает** абсолютный `paths.logs` в конфиг.
Дополнительно `src/llm.py:25`, `src/parsing.py:31`, `src/dashboard_data.py:41`
используют `logging.getLogger(__name__)` = `src.*`, а файловый handler навешен
только на logger `lifeos` (`src/main.py:118`) → их сообщения в ротируемый файл
не попадают (проверено: `dashboard: не читается шаблон …` видно только в stderr,
в `data/logs/agent.log` этой строки нет).

**Симптом.** Пользователь по README открывает `~/Library/Logs/LifeOS/agent.log`
и не видит почти ничего (там только stderr-WARNING), а вся полезная картина
(старт сессий, ролловер, запись в Obsidian) — в другом файле, который нигде не
документирован. Ошибки LLM/дашборда/парсинга в ротируемый лог не пишутся вовсе.

**Фикс.** (а) Настроить общий handler: `logging.getLogger("src").addHandler(...)`
или использовать имена `lifeos.*` во всех модулях; (б) в `install.sh` при
создании/обновлении конфига выставлять `paths.logs` в абсолютный `$LOG_DIR`
(и `paths.dashboard_out` при желании), либо поддержать `LIFEOS_LOG_DIR` в
`_setup_logging`; (в) привести plist/README/ТЗ к одному фактическому пути.

## P2 (мелкое; можно после установки)

**Данные и эвристика (fallback без LLM)**
1. `src/parsing.py:612-618` — в fallback `metrics` всегда `{}` (это соответствует ТЗ §3.4), но из-за этого `heuristic_metrics()` (`src/parsing.py:489`) **нигде не вызывается** (только тесты). Без LLM дашборд почти пуст: сон/вода/настроение не строятся, хотя пользователь их называет. Предложение: вызывать `heuristic_metrics()` в fallback (или отдельным флагом), либо убрать функцию из публичного API.
2. `src/parsing.py:455-469,520-541` — эвристика часов: «работал 14 часов сегодня» → `sleep_h=14`; «встреча 30 минут» → `duration_min=30` (и это засчитывается как тренировка в `src/dashboard_data.py:867-875`, где `duration>0` проверяется раньше негативных маркеров «не тренировался»). Предложение: требовать контекст сна/тренировки рядом с числом и/или проверять негативные маркеры до метрик.
3. `src/parsing.py:145-171` — категория по словам: ответ на утренний вопрос «1) отчёт 2) зал 3) магазин» → `training`, «Цель по бегу: 5 км» → `training` (а не `tasks`/`goals`). Предложение: при наличии ключевых слов слота отдавать приоритет слоту, а не «первой по порядку» категории.

**Поведение сессий/слотов**
4. `src/scheduler.py:330-344` — `tick()` сначала `_tick_slots`, потом `_tick_overdue`: при старте с сессией вчерашнего дня первый тик пропускает сегодняшний слот (сессия «занята»), старт происходит только на втором тике (~20 с). Небольшая задержка, но логичнее сначала закрывать просроченные сессии.
5. `src/scheduler.py:529-543` — `last_rollover` пишется **до** работы; если `sync_pending`/цели/дашборд упали — повтора в этот день не будет (только завтра). Предложение: писать маркер после успеха (или в `finally` с флагом).
6. `src/scheduler.py:352-358,402-404` — «мягкий вечерний пинг» при дефолтном `catchup_minutes=180` **недостижим**: максимальное опоздание вечера 21:30→23:59 = 149 мин < 180, поэтому вместо пинга всегда стартует сессия. Плюс `schedule.catchup_minutes` и `soft_ping` не описаны в `config/config.example.json`. Предложение: описать ключи и/или уменьшить catchup для вечера.
7. `src/scheduler.py:857-865` — если `prompts.followup_is_skip()` вернул `False`, запасной `_is_ok()` (`:1318`) не используется; ответ модели «Хорошо»/«Готово» вместо «OK» будет отправлен пользователю как «уточняющий вопрос». Предложение: `return helper(reply) or _is_ok(reply)`.
8. `src/main.py:367-378` — `--once` не берёт pid-лок: при работающем агенте можно запустить второй процесс, который будет конкурировать за `getUpdates` (409) и может «увести» апдейты у живого бота.

## Качество промптов brain (ТЗ §3.2, §3.4; проверено чтением + прогонами)

**Соответствует ТЗ:**
* `system_prompt()` (`src/prompts.py:56-80`) — русский, «ты», тёплый и конкретный,
  запрет лести/морали/диагнозов и выдумывания фактов, «1–2 предложения, один
  вопрос за раз», уточнение общих ответов («норм», «ок»). Это ровно §3.2 ТЗ.
* `scripted_questions()` (`src/prompts.py:110-150`) — утро: план/3 задачи/цели;
  день: еда/вода/энергия; вечер: тренировка/задачи/еда/настроение/мысли/завтра;
  неделя: итоги. Совпадает с ТЗ §3.2 и подробность высокая (просят порции, время,
  шкалы 1–5, «что перенёс и почему»).
* `followup_messages()` (`src/prompts.py:221-244` + `_FOLLOWUP_RULES:163-172`) —
  строгий контракт «ровно OK или один короткий вопрос», без предисловий, без
  повторения исходного вопроса; история диалога подмешивается и не дублирует
  текущий ответ (`_history_to_messages:177-220`, поддерживает оба формата истории).
  В связке с `scheduler._maybe_followup` соблюдается ТЗ: уточняем только короткий
  (<30 символов) ответ и не более `max_followups` (по умолчанию 2).
* `parse_messages()` (`src/prompts.py:332-360` + `_EXTRACTION_RULES:244-278`) —
  строго JSON `{category,title,text,metrics}`, few-shot примеры обычными ходами
  диалога, «только явное, ничего не додумывать», «не подставляй нули и средние»,
  явные примеры нормализации («два литра → 2000 мл», «полтора часа → 90 мин»,
  «два часа тренировки — это duration_min, а не sleep_h»). Это лучшая часть
  промптов, галлюцинаций метрик не провоцирует.
* `parsing._sanitize_metrics()` (`src/parsing.py:369-390`) валидирует ответ модели:
  только известные ключи, диапазоны (сон 0–24 ч, вода 0–20000 мл и т.п.), шкалы
  1–5 прижимаются, мусор отбрасывается — даже «фантазии» модели не попадут в БД.
  `parse_answer` не бросает исключений и корректно уходит в fallback без LLM
  (проверено на `None`, мусорном JSON, ответе не-dict, битом `now_iso`).
* Fallback без LLM существует и работает в e2e: вопросы идут скриптованные,
  записи сохраняются, `metrics` пустые — как требует ТЗ §3.4.

**Замечания (мелкие):** `weekly_prompt()` (`src/prompts.py:437`) не используется
(недельный дайджест — фаза 2, нормально); `followup_is_skip` не ловит «Хорошо»
(см. P2-7); `distance_km` в промпте шире схемы ТЗ (P2-26).

## Итоговая оценка готовности к живой установке

**Код в хорошем состоянии:** интерфейсы INTERFACES.md соблюдены (проверены
сигнатуры всех публичных функций, схемы entry/сессий/kv, формат блоков
Obsidian, схема `collect_data`), «никогда не бросать» для llm/vault/dash
выполняется (проверено на мусорных входах), SQL только параметризованный,
`eval/exec/subprocess` нет, сеть только Telegram/LLM, секреты в код/логи не
попадают (кроме найденного краевого пути P1-3). Модули не имеют циклических
импортов, код совместим с Python 3.9.6 и 3.13. Аккуратно сделаны: идемпотентность
записей/слотов (маркеры, `last_slot`), восстановление недописанных записей,
catch-up/TTL сессий, атомарная запись файлов, обход багов Telegram 429/409.
Дашборд — self-contained, без CDN, данные встроены, плейсхолдеры заменяются,
JS исполняется без ошибок и без «undefined/NaN» на реальных/пустых/грязных данных.

**Живой установке мешают четыре вещи (P1):** повторная обработка апдейтов из-за
несохранённого offset (дубли записей/сдвиг сессии), небезопасный `--dry-run`,
который портит рабочее состояние и даже может писать в живую базу Obsidian,
возможная утечка токена в лог при опечатке в `api_base`, и расхождение путей
логов с ТЗ/README, из-за которого диагностика на машине пользователя будет
затруднена.

**Рекомендация:** исправить P1-1 и P1-2 (обязательно, оба небольшие), затем
P1-3 и P1-4 (желательно, тоже небольшие); после этого можно ставить на машину
с реальным токеном. P2 — по мере сил; критичные из них для первого дня
эксплуатации: №18 (git/секреты) и №20 (безопасный `rm -rf` в установщике).
